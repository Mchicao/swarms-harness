# SWARMS State Contract v2

Status: Draft

Tracks: R-003, R-007, R-011, R-012, R-020

## Purpose

This contract defines the durable interface between the runtime, observers, recovery logic, reporting, and external tooling. Producers and readers must not rely on undocumented fields or silently reinterpret corrupt/missing data.

Machine-readable schemas live in `schemas/state-v2/`.

## Versioning

Every v2 JSON document contains:

```json
{
  "schema": "swarms.task-state",
  "schema_version": 2
}
```

Rules:

- adding an optional field is backward-compatible within v2;
- changing meaning, type, requiredness, or identity rules requires a new major schema version;
- readers may tolerate unknown optional fields but must reject an unknown major version;
- writers must never emit fields promised by documentation with a different type.

## Task snapshot

Each task snapshot is a complete current-state projection, not an event.

Required identity and graph fields:

- `run_id`;
- `task_id`: canonical runtime ID;
- `source_id`: exact plan/compiler ID;
- `stage`;
- `role`;
- `requested_route`;
- `effective_route`;
- `needs`: canonical dependency task IDs;
- `parent_task_id` and `depth` when generated by a workflow compiler.

Required lifecycle fields:

- `status`: `pending`, `running`, `succeeded`, `failed`, `blocked`, or `cancelled`;
- `attempt` and `max_attempts`;
- `created_at`, `started_at`, `updated_at`, and `finished_at` as RFC 3339 UTC timestamps where applicable;
- `terminal_reason` for terminal states;
- `error` as a typed public error summary without secrets or raw prompts.

Required observability fields:

- worker-log path and current byte count;
- last activity timestamp;
- session reuse metadata;
- artifact and verification outcomes;
- usage object with completeness metadata.

The producer writes snapshots atomically. A reader must either observe the previous complete snapshot or the new complete snapshot, never a partially written document.

## Event stream

`events.jsonl` is append-only. Every line is an independently valid event document with:

- `schema = "swarms.event"`;
- `schema_version = 2`;
- collision-resistant `event_id`;
- `run_id`;
- optional `task_id`;
- RFC 3339 UTC `timestamp`;
- monotonic per-run `sequence` assigned by the writer;
- typed `kind`;
- typed `data` object.

Malformed historical lines are quarantined and reported; they must not cause valid later events to be discarded.

Event kinds include:

- run/task lifecycle transitions;
- retry scheduled/started;
- steering accepted/rejected/applied;
- session created/reused/rejected;
- quota decision;
- process terminal outcome;
- verification and artifact outcome;
- persistence degradation;
- usage observed and report completed.

## Usage and completeness

Usage uses numeric optional fields, never string sentinels:

```json
{
  "input_tokens": 1200,
  "output_tokens": 300,
  "total_tokens": 1500,
  "source": "provider_event",
  "complete": true
}
```

When usage is unavailable:

```json
{
  "input_tokens": null,
  "output_tokens": null,
  "total_tokens": null,
  "source": "unavailable",
  "complete": false
}
```

Run reports include:

- total task count;
- tasks with complete usage;
- tasks with partial usage;
- tasks with unavailable usage;
- aggregate totals only for known values;
- `aggregate_complete`, which is true only when every included task has complete usage.

A partial aggregate must never be displayed as a complete run total.

## Persistence behavior

Critical durable state:

- plan/checkpoint identity;
- task snapshots;
- session mappings used for resume;
- steering inbox/claim/audit records;
- final report.

Critical write failure terminates or blocks the affected operation. Telemetry-only failure may allow execution to continue only when a `persistence_degraded` event/state flag can still be recorded through an independent path.

Atomic write requirements:

1. create a unique temporary file in the destination directory;
2. write the complete payload;
3. flush and sync according to the durability class;
4. atomically replace the destination;
5. sync the directory when the platform requires it for rename durability.

A fixed `.tmp` name is prohibited because concurrent writers can collide.

## Corruption handling

- Invalid task/session/checkpoint JSON is moved to a quarantine directory with a collision-resistant name.
- The runtime reports the original path, parsing category, quarantine path, and recovery decision.
- Corrupt session state is never silently replaced by an empty session map.
- Resume fails closed when checkpoint identity cannot be proven.
- Readers may continue processing other valid tasks but must surface corruption visibly.

## Steering durability

Steering message and event IDs use UUIDv7, ULID, or equivalent collision-resistant sortable identifiers. Claiming messages must not strand an entire batch because one entry is malformed.

Required algorithm:

1. atomically claim an inbox segment;
2. parse entries independently;
3. apply valid entries in order;
4. quarantine malformed entries;
5. persist an audit record for every accepted, rejected, and malformed entry;
6. delete the claimed segment only after all outcomes are durably recorded.

## Golden fixtures and compatibility tests

Required fixtures:

- pending, running, succeeded, failed, blocked, and cancelled task snapshots;
- complete, partial, and unavailable usage;
- retry history;
- session reuse;
- steering accepted/rejected/malformed;
- corrupt state quarantine;
- a mixed run report.

Required tests:

- Rust producer output validates against JSON Schema;
- state reader loads every golden task/run fixture;
- writer atomicity fault injection at each write/flush/rename step;
- concurrent steering writers/claimers;
- deterministic report serialization;
- v1 compatibility reader or explicit migration rejection.

## Acceptance gate

The existing `STATE_CONTRACT.md` must be replaced or marked historical only after Rust producers, state readers, reports, and golden tests all implement this v2 contract. Documentation alone does not close the finding.
